# 资源冲突检测规则与提示机制

> 本规范定义多任务并行执行场景下的资源冲突检测规则、提示机制与处理流程。
> 配合 `templates/conflict-matrix.md` 与 `registry/conflict-matrix.md`（实例）使用。

---

## 一、资源分类

### 1.1 按占用类型

| 类型 | 标记 | 说明 | 典型场景 |
| --- | --- | --- | --- |
| 只读 | R | 仅读取，不修改 | 调用 API、查询数据库、读取配置 |
| 写入 | W | 修改现有内容 | 修改代码文件、更新配置、变更 schema |
| 独占 | X | 排他性占用，不允许任何其他任务访问 | 生产部署、数据库迁移、环境重建 |

### 1.2 按资源类别

| 类别 | 示例 | 默认占用假设 |
| --- | --- | --- |
| 代码模块 / 文件 | `server/src/controllers/auth.ts` | 修改即 W |
| API 接口 | `POST /api/v1/auth/login` | 新增即 W，调用即 R，修改契约即 X |
| 数据库表 | `User`、`Analysis` | 查询即 R，schema 变更即 X |
| 环境变量 | `DATABASE_URL` | 读取即 R，新增/修改即 W |
| 运行环境 | 本地 / 预发 / 生产 | 使用即 ✓，生产部署窗口即 X |
| 第三方服务 | 飞书 OAuth、AI 模型 API | 调用即 R，配置变更即 W |
| 静态资源 | 图片、视频、字体 | 引用即 R，替换即 W |

## 二、冲突判定规则

### 2.1 核心规则矩阵

| 任务 A \ 任务 B | R | W | X |
| --- | --- | --- | --- |
| **R** | ✓ 无冲突 | ✓ 无冲突 | ⚠️ 冲突 |
| **W** | ✓ 无冲突 | ⚠️ 冲突 | ⚠️ 冲突 |
| **X** | ⚠️ 冲突 | ⚠️ 冲突 | ⚠️ 冲突 |

### 2.2 详细规则

**规则 1：W × W 冲突**
- 同一资源被两个及以上任务标记为 W
- 例外：同一任务多次 W 不算冲突
- 严重度：高（代码冲突可能导致合并困难）

**规则 2：X × 任意 冲突**
- 同一资源被一个任务标记为 X，另一任务为任意标记
- 严重度：阻断（独占期间不允许任何访问）

**规则 3：API 契约变更冲突**
- 任务 A 修改某 API 的请求/响应结构（X），任务 B 调用该 API（R）
- 严重度：高（可能导致调用方失败）

**规则 4：数据库 schema 变更冲突**
- 任务 A 修改表结构（X），任务 B 查询该表（R）
- 严重度：阻断（schema 变更期间表不可用）

**规则 5：生产部署窗口冲突**
- 多个任务都需要在生产环境部署
- 严重度：高（需串行部署，避免相互影响）

**规则 6：依赖冲突**
- 任务 A 依赖任务 B 的产出，但 B 尚未完成
- 严重度：中（A 需等待 B）

### 2.3 非冲突情况

- 多任务只读同一资源（R × R）
- 多任务修改不同文件（即使同一目录）
- 多任务使用同一本地开发环境（独立端口）
- 多任务调用同一 API 的不同端点

## 三、检测流程

### 3.1 触发时机

| 事件 | 是否触发检测 |
| --- | --- |
| 新任务创建 | ✓ 必须 |
| 任务资源声明变更 | ✓ 必须 |
| 任务状态变更（启动/阻塞/完成） | ✓ 必须 |
| 日常同步（每日） | ✓ 建议 |
| 任务步骤完成 | ✗ 不需要 |

### 3.2 检测步骤

```
1. 读取 registry/conflict-matrix.md
   ↓
2. 遍历每个资源行
   ↓
3. 统计该资源上各任务的占用标记
   ↓
4. 应用冲突判定规则（2.1 矩阵）
   ↓
5. 若发现冲突，记录到「冲突清单」
   ↓
6. 输出冲突报告（含资源、涉及任务、类型、严重度）
   ↓
7. 在 registry/active-tasks.md 并行执行矩阵标记 ✗
   ↓
8. 通知相关任务负责人
```

### 3.3 手动检测清单

每次任务创建或资源变更后，按以下清单逐项检查：

- [ ] 新任务的 W 资源是否与现有任务的 W 资源重叠？
- [ ] 新任务的 X 资源是否与现有任务的任何资源重叠？
- [ ] 新任务是否修改了被其他任务调用的 API 契约？
- [ ] 新任务是否变更了被其他任务查询的数据库表 schema？
- [ ] 新任务的生产部署是否与现有任务部署窗口重叠？
- [ ] 新任务是否依赖尚未完成的任务产出？

## 四、提示机制

### 4.1 提示渠道

| 渠道 | 用途 | 触发条件 |
| --- | --- | --- |
| `registry/active-tasks.md` 并行执行矩阵 | 可视化标记 ✗ | 检测到冲突时 |
| `registry/conflict-matrix.md` 冲突清单 | 详细冲突信息 | 检测到冲突时 |
| 任务 `changelog.md` | 任务级记录 | 任务被冲突影响时 |
| Git 提交信息 | 历史追溯 | 冲突处理提交时 |

### 4.2 提示模板

**冲突提示（写入受影响任务的 changelog）**：

```
### v0.X.0 — YYYY-MM-DD

- **变更类型**：blocked（资源冲突）
- **变更人**：<检测人>
- **变更内容**：
  - 与 TASK-YYYY 在资源 <资源路径> 上存在 W × W 冲突
  - 任务进入阻塞状态，等待 TASK-YYYY 完成
- **影响范围**：任务执行
- **状态变更**：🔵 IN_PROGRESS → 🟡 BLOCKED
- **预计解除**：YYYY-MM-DD（TASK-YYYY 计划完成时间）
- **关联冲突**：C-XXX
```

**冲突解除提示**：

```
### v0.X.0 — YYYY-MM-DD

- **变更类型**：unblocked（冲突解除）
- **变更人**：<检测人>
- **变更内容**：
  - TASK-YYYY 已完成，资源 <资源路径> 占用释放
  - 任务恢复进行中状态
- **状态变更**：🟡 BLOCKED → 🔵 IN_PROGRESS
- **关联冲突**：C-XXX（已解除）
```

## 五、冲突处理策略

### 5.1 串行化（首选）

适用场景：两个任务都需要修改同一文件

操作：
1. 评估两任务优先级与截止日期
2. 高优先级或截止日期近的任务先执行
3. 低优先级任务标记为 🟡 BLOCKED，依赖高优先级任务
4. 高优先级任务完成后，通知低优先级任务继续

### 5.2 资源拆分（次选）

适用场景：两个任务修改同一文件的不同部分

操作：
1. 将共享文件按职责拆分为多个文件
2. 每个任务修改独立文件
3. 在公共入口（如 index.ts）中聚合
4. 更新冲突矩阵，标记为无冲突

### 5.3 分支隔离（适用 Git 工作流）

适用场景：两个任务都需要修改同一文件，但可并行开发

操作：
1. 每个任务在独立 Git 分支开发
2. 完成后分别提交 PR
3. 按 PR 顺序合并，第二个 PR 处理合并冲突
4. 注意：合并冲突可能引入风险，需充分测试

### 5.4 任务合并（最后手段）

适用场景：两个任务高度耦合，无法独立完成

操作：
1. 将两个任务合并为一个
2. 选择主任务 ID 保留，副任务标记为 ⚫ CANCELLED（原因：合并至 TASK-XXXX）
3. 在主任务的 plan.md 中合并步骤
4. 在主任务的 changelog 中记录合并事件

## 六、冲突严重度与处理时限

| 严重度 | 触发条件 | 处理时限 | 升级条件 |
| --- | --- | --- | --- |
| 阻断 | 生产环境 X 占用冲突、DB schema X 冲突 | 立即处理 | 1 小时内未解决 → 升级至负责人 |
| 高 | 核心代码 W × W 冲突、API 契约变更冲突 | 当日内处理 | 1 日内未解决 → 升级至负责人 |
| 中 | 辅助文件 W × W 冲突、配置文件冲突 | 下一迭代前 | 下一迭代前未解决 → 取消或合并任务 |
| 低 | 理论冲突，实际影响小 | 记录跟踪 | 演变为高严重度时升级 |

## 七、冲突记录与统计

### 7.1 冲突 ID 规则

- 格式：`C-XXX`，三位数字递增
- 在 `registry/conflict-matrix.md` 的「冲突清单」中分配

### 7.2 冲突生命周期

```
检测 → 记录 → 处理 → 解除 → 关闭
 ↓       ↓       ↓       ↓       ↓
新增    待解除  处理中  已解除  已关闭
```

### 7.3 统计指标

建议定期统计以下指标用于流程改进：

- 冲突总数 / 任务数 = 冲突密度
- 平均冲突处理时长
- 按严重度分布
- 按资源类别分布
- 重复冲突资源（同一资源多次冲突 → 考虑重构）

## 八、实战案例:2026-08-04 项目方向校准

> 本案例基于 `.trae/documents/context-log-2026-08-04.md` 的真实项目偏差事件,作为冲突检测的实战参考。

### 8.1 案例背景

2026-08-04 发现项目偏离主体方向:

- 官网独立部署到 GitHub Pages,未与主应用挂载
- P2 服务端配置修复完全未实施(gzip/HTTPS/安全头)
- deploy-gh-pages.cjs 错误推送 dist/(主应用)而非官网
- QA 工作覆盖 prototype/(非产品代码),未覆盖生产代码
- P3 任务分散在 mobile/admin,与核心目标脱节
- nginx-site.conf 过度简化(27行,无生产配置)

### 8.2 偏差根因分析

| 根因 | 说明 | 本系统如何预防 |
|------|------|---------------|
| 需求理解偏差 | agent 配置文档将官网定义为"独立 GitHub Pages",与用户真实诉求"官网+使用入口一体化"冲突 | 在 `tasks/TASK-*/README.md` 的「任务目标」字段强制写明可验证结果,且需用户确认 |
| 技术决策失误 | deploy-gh-pages.cjs 错误推送主应用;nginx-site.conf 过度简化 | 通过 `registry/conflict-matrix.md` 声明资源占用,会暴露「同一文件被多任务 W」或「部署目标与产物不匹配」 |
| 资源分配问题 | QA 精力投入 prototype/;P3 优先开发 mobile/admin 扩展 | 通过 `registry/active-tasks.md` 的「优先级」字段与「依赖任务」字段,可视化任务优先级与依赖,避免低优先级任务抢占资源 |
| 沟通协调不足 | agent 配置文档与用户诉求长期不一致 | 通过 `tasks/TASK-*/changelog.md` 记录每次变更,任何方向调整必须追加 `scope` 记录并通知相关方 |

### 8.3 本系统可预防的偏差类型

| 偏差类型 | 本系统检测机制 |
|---------|--------------|
| 官网与主应用挂载关系错误 | 任务创建时声明资源占用,若官网资源未在主应用任务中声明,会触发依赖检查 |
| 同一文件被错误部署 | 冲突矩阵会标记「同一资源 W × W」,提示任务负责人复核 |
| QA 资源浪费在非生产代码 | 任务创建时需声明资源占用,`prototype/*` 与 `src/*` 会被区分 |
| 任务优先级偏离核心目标 | `active-tasks.md` 总览表会暴露「P0 任务未启动而 P2 任务进行中」的异常 |
| 部署配置简化 | 任务 DoD(验收标准)必须明确,如「nginx 配置行数」或「安全头清单」 |

### 8.4 案例启示

1. **任务创建时必须明确目标与验收标准**:本系统的 `task-template.md` 强制要求填写 DoD,可防止「目标模糊导致方向偏离」
2. **资源占用必须细化到文件级**:`registry/conflict-matrix.md` 要求细化到文件路径,可暴露「部署目标与产物不匹配」
3. **任务优先级必须可视化**:`active-tasks.md` 的总览表让所有任务优先级一目了然,可防止「低优先级任务抢占资源」
4. **变更必须可追溯**:`changelog.md` 记录每次变更,任何方向调整必须追加 `scope` 记录,可防止「静默偏离」

## 九、检测自动化建议(未来演进)

> 当前系统为手动检测,未来可考虑自动化:

### 9.1 自动冲突检测脚本(规划中)

可开发一个简单的脚本扫描 `registry/conflict-matrix.md`:

```powershell
# 伪代码
foreach ($resource in $resourceRows) {
  $wCount = ($resource.WMarks | Where-Object { $_ -eq "W" }).Count
  $xCount = ($resource.XMarks | Where-Object { $_ -eq "X" }).Count
  if ($wCount -ge 2 -or $xCount -ge 1 -and ($wCount -ge 1 -or $xCount -ge 2)) {
    Write-Warning "冲突检测:资源 $($resource.Path) 存在 W×W 或 X×任意 冲突"
  }
}
```

### 9.2 与 Git Hooks 集成(规划中)

- `pre-commit` hook:提交前自动扫描 `registry/conflict-matrix.md`,若有未处理冲突则警告
- `commit-msg` hook:校验提交信息是否符合 Conventional Commits + 任务 ID 格式

### 9.3 与 CI/CD 集成(规划中)

- GitHub Actions:每次 PR 自动运行冲突检测脚本,若有冲突则在 PR 评论中提示
- 定期任务:每日扫描 `active-tasks.md`,生成「日报」摘要
